# 练 4 · 部署方案对比表 + 推荐配置单（报价包第 4 件）

> 对应第 04–05 章 · 要求：API、自建、混合三方案都算一遍，含盈亏平衡点与取舍理由；显存按「权重 + KV Cache + 运行开销」三件套计算。

## 1. 先过决策表

| 判断项 | 本项目情况 | 倾向 |
| --- | --- | --- |
| 数据合规 | 患者姓名、电话、住院号在 HIS 内网；医疗行业强监管 | **私有化 / 混合**（纯 API 一票否决） |
| 用量规模 | 月 Token 1,437 万（0.14 亿），峰值并发 8 路 | 倾向 API（远低于自建平衡点） |
| 模型能力 | 7B–14B 开源模型可满足制度问答与随访草稿 | 可用私有化，但非必须 |
| 运维能力 | 信息科无 GPU 运维经验，无 7×24 值班 | 倾向 API / 混合 |
| 响应延迟 | 内网工作台，P95 < 3 秒可接受 | 均可，API 需实测 |

**结论：数据合规一票否决纯 API；用量太小否决全私有化；选混合。**

## 2. 显存三件套（为 B 方案算清，避免只按权重买卡）

```text
模型：14B INT4（量化后权重 ≈ 8.5 GB）
KV Cache：192 KB/Token × 4,096 Token × 8 并发 ÷ 1024² ≈ 6.00 GB
运行开销：15%
总显存 =（8.5 + 6.00）× 1.15 ≈ 16.67 GB / 台
结论：单卡 RTX 4090 24G 可跑；生产需 2 台主备（双副本）
```

> 若上下文从 4K 提到 8K，KV 翻倍到 12 GB，总显存约 23.6 GB，24G 卡即到临界——**上下文和并发是可谈判的业务参数**，必须先问清峰值再买卡。

## 3. 三方案年成本对比

| 方案 | 部署内容 | 年成本 | 3 年 TCO | 合规 | 运维要求 | 结论 |
| --- | --- | ---: | ---: | --- | --- | --- |
| A 纯云端 API | 患者数据经公网网关直连云端 API | 4,660.27 | 13,980.81 | **不合规**（PII 出内网） | 低 | 仅作成本基准，淘汰 |
| B 全私有化 | 2 台单卡 RTX 4090 工作站（14B INT4）主备 | 71,660.16 | 214,980.48 | 合规 | 高（GPU 运维 + 模型更新） | 成本是 C 的 6.7 倍，淘汰 |
| **C 混合（推荐）** | 敏感数据留内网；脱敏文本调云端 API；内网 2 台 8C16G 主备 | **10,660.27** | **31,980.81** | 合规（PII 不出内网 + 审计留痕） | 中（沿用现有虚拟化） | **推荐** |

**B 方案年成本拆解**：整机 2 × 45,000 = 90,000，3 年折旧 30,000/年；电费 1.8 kW × 8,760 h × 0.8 元 × PUE 1.4 = 17,660/年；运维 0.2 人 × 12 万 = 24,000/年。

**C 方案年成本拆解**：模型 546.67 + 短信 153.60 + 内网服务器 9,960 = **10,660.27**（与练 1 服务器 + 模型 + 数据三块一致）。

## 4. 盈亏平衡点：用量到哪条线才该自建

```text
私有化月固定成本 = 71,660.16 ÷ 12 ≈ 5,971.68 元
API 加权综合单价 = (6,500×2.181 + 900×7.302) ÷ 7,400 ≈ 2.80 元/百万 Token
临界月用量 = 5,971.68 ÷ 2.80 ≈ 2,129.83 百万 Token ≈ 21.3 亿 Token/月
本项目基准用量 = 14.37 百万 Token ≈ 0.14 亿 Token/月（仅为临界值的 0.7%）
```

**结论：本项目用量离自建平衡点差约 148 倍，自建在三年内都不可能回本。** 即使未来扩到全院（约 6 倍用量），仍低于临界值；只有接入全院 + 影像/长文档等场景后才需重新评估。

## 5. 推荐配置单（C 方案）

| 部件 | 配置 | 数量 | 依据 |
| --- | --- | --- | --- |
| 应用服务器 | 8 核 16G，200GB SSD | 2（主备） | 320 例/月、峰值 8 并发，CPU 峰值 < 40% |
| GPU | 无（模型走云端 API） | 0 | 低于 21.3 亿 Token/月，自建闲置 |
| 数据库 | 复用院内 PostgreSQL / MySQL 实例 | 1 | 随访任务 + 审计日志，日增 < 50MB |
| 存储 | 1TB 备份空间 | 1 | 日志留存 6 个月，满足医疗审计 |
| 网络 | 内网 DMZ + 脱敏网关 + 出向白名单 | 1 套 | 仅脱敏文本出网，禁止患者标识 |
| 并发能力 | 峰值 8 路，P95 < 3 秒 | — | 试点 2 科室，日峰约 60 次请求 |
| 高可用 | 双节点主备，切换 < 5 分钟 | — | 试点期承诺 99.5%，不承诺 99.9% |

## 6. 取舍理由（为什么不选另外两个）

- **不选 A**：成本最低（4,660 元/年），但患者标识会出内网，触碰医疗合规红线；一旦被质控办否决，项目直接停摆，省下的 6,000 元毫无意义。
- **不选 B**：合规没问题，但年成本 71,660 元是 C 的 6.7 倍，且需要 GPU 运维能力与模型更新流程；在 0.14 亿 Token/月的用量下，90% 的算力会闲置。
- **选 C**：把「敏感数据」与「模型能力」拆开——数据留内网、只把脱敏文本送出去；既过合规，又保留云端模型能力，年成本仅 1.07 万元。风险是依赖公网 API 延迟与厂商调价，已用「P95 实测 + 调价传导条款」兜住。
