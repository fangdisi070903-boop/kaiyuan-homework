## 四、人工检查与修正记录

| 序号 | 问题 | 处理方式 |
| --- | --- | --- |
| 1 | 初稿未检查 `GetBlockNum()` 是否为 0 | 增加 `ASSERT`，避免除零 |
| 2 | 初稿没有说明 `DataCopy` 的 32B 对齐要求 | 在 Kernel 注释与 Host 侧增加对齐检查 |
| 3 | 初稿的 tile 循环次数写死为 `tileNum`，与 Double Buffer 不匹配 | 改为 `tileNum * BUFFER_NUM` |
| 4 | 初稿未处理总长度不能被 `block_dim` 整除的情况 | Host 侧增加整除与对齐校验，并返回明确错误 |
| 5 | 初稿的 Tiling 结构缺少命名空间，Host 侧无法直接使用 | 统一放入 `optiling` 命名空间 |
| 6 | 初稿声称“已在昇腾环境验证” | 删除不实表述，改为“未编译，仅完成 CPU 算法验证” |
| 7 | 初稿的 Python 参考实现依赖 NumPy | 改为纯 Python，降低环境依赖，便于任何机器复现 |

## 六、结论

大模型可以快速给出 Ascend C 算子的结构框架，但在以下方面必须人工把关：

- 硬件约束（对齐、缓冲区大小、队列深度）；
- Tiling 与数据切分的边界条件；
- 不同 CANN 版本的 API 差异；
- 不能把“生成代码”等同于“已验证代码”。

因此本次交付将代码定位为“初步代码”，并单独提供可执行的 CPU 金标准验证，保证仓库中的每条结论都有证据。
