# 开源软件许可证合规分析——以 PM2 为例

## 一、选取的开源项目

本文选取 PM2（Process Manager 2）作为检测对象。PM2 是 Node.js 生态中广泛使用的进程管理与守护工具，支持进程守护、负载均衡、日志管理与集群模式，常用于 Node.js 服务的生产部署。项目托管于 GitHub（https://github.com/Unitech/pm2），本次扫描版本为 7.1.2，对应 commit `7a7fb4e22e9a26ec79c870ce8daafd2f78b648d1`，许可证为 AGPL-3.0。

选择该项目有三点考虑：第一，PM2 采用强 copyleft 的 AGPL-3.0，且常用于对外提供网络服务，覆盖“分发义务”与“网络交互义务”两个合规重点；第二，其生产依赖共 44 个第三方包，覆盖 MIT、ISC、Apache-2.0、Python-2.0、Public Domain 等类型，可检验工具对复杂元数据的识别能力；第三，项目规模适中，扫描结果可以逐项人工复核。

## 二、许可证合规工具的安装过程及遇到的问题

检测环境为 macOS 26.6.2（arm64），系统未预装 Node.js。首选课程资料第 27 项 ScanCode Toolkit，执行 `pip install scancode-toolkit==31.2.6` 时，依赖 PyICU 因缺少 ICU 开发头文件与 `pkg-config` 编译失败，报错为“Please install pkg-config on your system or set the ICU_VERSION environment variable”。由于 PyPI 未提供 macOS arm64 的 PyICU 预编译包，本机也没有 Homebrew，故放弃该工具，改用课程资料第 18 项 **Licensee.js**（npm 包名 `licensee`）作为主检测工具，并安装 `license-checker` 做交叉验证。最终版本为 licensee 12.0.2、license-checker 25.0.1、Node.js v20.18.1，检测规则为 `--osi`。

```bash
npm install -g licensee@12.0.2 license-checker@25.0.1
cd pm2 && npm install --ignore-scripts --no-audit --no-fund
licensee --osi --production
license-checker --production --json
```

安装与运行中遇到的主要问题：

1. 系统没有 Node.js 与 npm，从 npmmirror 下载 Node v20.18.1 的 darwin-arm64 二进制包并加入 `PATH`。
2. GitHub 直连克隆 PM2 时报 `Error in the HTTP2 framing layer`，改用 `codeload.github.com` 下载源码 tar.gz。
3. licensee 首次运行要求读取 `.licensee.json`，否则报错；本次不生成配置文件，直接传入 `--osi` 规则参数。
4. 为避免第三方依赖的 `postinstall` 脚本修改本机环境，安装依赖时使用 `npm install --ignore-scripts`。
5. 部分依赖的许可证元数据不规范：`@pm2/js-api` 写作 `Apache-2`（不是合法 SPDX 标识），`cli-tableau` 缺少 `license` 字段，`tv4` 的 `license` 为数组。工具因此将其判为未批准，需要人工复核。
6. licensee 在存在未批准包时退出码为 1，这是预期行为，不代表工具执行失败；报告中保留完整输出并单独分析。

执行 `licensee --osi --production` 与 `license-checker --production --json` 后，生产依赖树的统计结果见表 1。44 个第三方包中，35 个为 MIT、5 个为 ISC，其余 4 个分别为 Apache、Python-2.0、MIT 与 Public Domain/MIT；PM2 自身为 AGPL-3.0，不计入依赖统计。

## 四、针对检测报告的详细分析

### 4.1 检测方法与充分性判断标准

本次检测采用“三层验证”：第一层用 licensee 按 OSI 白名单扫描依赖元数据；第二层用 license-checker 独立统计许可证分布，交叉核对包数量与许可证类型；第三层对每个未批准项打开包内 `package.json` 与 `LICENSE` 文件人工复核。充分性判断标准设为四项：生产依赖覆盖率 100%（44/44）；直接依赖与传递依赖均纳入；每个异常项都有可核对的原始文件依据；命令、版本与原始输出齐全，第三方可按 `scan/commands.sh` 复现。四项均满足，因此认为检测对“依赖许可证元数据”这一目标是充分的。

### 4.2 许可证兼容性分析

PM2 自身采用 AGPL-3.0，其 44 个生产依赖全部为宽松许可或 MIT 双许可，不包含 GPL-2.0-only、SSPL 等与 AGPLv3 存在冲突的许可证。宽松许可允许被并入采用更强 copyleft 的作品，因此依赖侧不存在许可证冲突；Apache-2.0 与 GPLv3/AGPLv3 按 FSF 的立场兼容，但分发时需保留其版权、许可与 NOTICE 文件，并注意专利条款。真正需要关注的是 PM2 自身的 AGPL-3.0 义务。

### 4.3 AGPL-3.0 的分发与网络服务义务

AGPL-3.0 在 GPLv3 的基础上增加了第 13 条“远程网络交互”条款：分发修改版或衍生作品时，必须以源码形式提供完整对应源码，保留版权与许可证声明，并在修改文件中作出显著说明；若用户通过计算机网络与修改版交互，必须提供获取对应源码的显著方式，且不得对源码收取额外费用；不得对许可证授予的权利附加额外限制；AGPL 不授予 PM2 名称、标识等商标使用权。仅内部使用、不对外分发也不提供网络交互时义务相对有限；一旦将 PM2 打包进容器镜像对外交付，或以 SaaS 形式提供服务，就需要提前准备源码获取方案与合规材料。

### 4.4 检测风险与局限

本次检测存在四类风险。一是元数据风险：3 个未批准项均源于 `license` 字段不规范，仅依赖元数据会产生误报，必须人工复核。二是范围风险：工具只扫描依赖，不解析 PM2 源码文件头，可能遗漏文件级双许可或例外条款。三是层级风险：未做二进制与容器镜像扫描，镜像中的系统包、静态链接库不在覆盖范围内。四是版本风险：本次基于 master 分支源码，结论只对当前版本成立。此外，BlueOak-1.0.0 等非 OSI 许可证会被规则拦截，需要结合分发场景判断，不能简单视为“不可用”。

### 4.5 总体合规策略与整改建议

建议建立“工具扫描 + 人工复核 + 法务判断”的三级流程：在 CI 中固定执行 `licensee --osi --production`，未通过即阻断合并；维护许可证白名单与例外审批；用 CycloneDX 或 SPDX 生成 SBOM，固定版本与哈希。针对本次问题，可向上游提交元数据修正：`Apache-2` 改为 `Apache-2.0`，`cli-tableau` 补充 `license` 字段，`tv4` 明确单一 SPDX 表达式。对外分发 PM2 时应随包提供 LICENSE、NOTICE、第三方声明与源码获取方式；以 SaaS 提供修改版时，应按 AGPL 第 13 条提供源码入口，并由法务评估商标与专利条款。依赖升级或镜像重建后应重新扫描。

## 五、结论

本次使用 Licensee.js 与 license-checker 对 PM2 7.1.2 的生产依赖进行了检测。44 个第三方依赖中 41 个通过 OSI 规则，3 个未通过项经人工复核均为元数据书写问题，实际均为宽松许可，依赖侧不存在 copyleft 冲突。项目的真实合规重点是自身 AGPL-3.0 在分发与网络服务场景下的源码提供义务。工具能发现元数据异常，但不能替代人工复核与法律判断；只有把扫描、SBOM、CI 门禁与分发材料结合，才能形成可审计的合规闭环。
